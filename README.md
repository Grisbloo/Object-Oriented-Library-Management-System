# Object-Oriented-Library-Management-System

# Final Project

## Description
In this project, you will analyze and design an object-oriented Library Management System and partially implement selected parts of your design.

The primary goal of the project is to demonstrate your ability to systematically transform software requirements into a well-designed object-oriented solution using the concepts and techniques covered throughout the semester.

Your system will represent a library that maintains a catalog of items and allows library members to search for, borrow, return, and reserve library items. Librarians will be able to manage library resources and member-related operations.

The primary emphasis of this project is on object-oriented analysis and design rather than building a complete application. You will be evaluated on the quality of your requirements analysis, object-oriented models, responsibility assignments, object collaborations, design decisions, and the consistency between your design and partial implementation.

This will be a team project. Students will form their own teams of 5 students.

## Project Requirements
Your Library Management System should support at least the following functionality.

### Library Catalog
1. The library maintains a collection of library items, such as books, audiobooks, DVDs, or other resources.
2. Each item should contain appropriate descriptive information, such as title, author/creator, item type, a unique identifier, and availability.
3. The library may have multiple copies of the same item.
4. Members should be able to browse or search the library catalog.

### Library Members
5. The system maintains information about registered library members.
6. A member can view the items they currently have borrowed.
7. A member can view relevant information about their borrowing activity.
8. The system should prevent invalid borrowing operations.

### Borrowing and Returning
9. A member can borrow an available library item.
10. The system should record the borrowing transaction.
11. Each borrowed item should have an appropriate due date.
12. A member can return an item they have borrowed.
13. When an item is returned, its availability should be updated.
14. The system should be able to determine whether an item is overdue.

### Reservations
15. If an item is currently unavailable, a member should be able to place a reservation.
16. The system should maintain information about outstanding reservations.
17. When an item becomes available, the appropriate reservation should be handled according to your team's design.

## Object-Oriented Analysis and Design

### 1. Requirements Analysis
Your team should analyze the project requirements and identify:
*   functional requirements;
*   relevant non-functional requirements;
*   system actors; and
*   major system functionality.

You may refine or clarify the provided requirements, but any significant assumptions should be documented.

### 2. Use Cases
Identify the important use cases for the system. For selected major use cases, provide:
*   use-case name;
*   primary actor;
*   preconditions;
*   main success scenario;
*   appropriate alternative/exception flows; and
*   postconditions.

Possible use cases include Borrow Item, Return Item, Search Catalog, and Reserve Item, but your team is responsible for determining the appropriate use cases.

### 3. Domain Model
Develop a domain model representing important concepts in the problem domain and their relationships. For example, you may discover concepts related to members, library resources, borrowing, and reservations.

### 4. System Sequence Diagrams
Create System Sequence Diagrams (SSDs) for selected major use cases. Your SSDs should show the important system events generated by external actors.

### 5. Operation Contracts
Create operation contracts for selected important system operations. Contracts should describe appropriate:
*   preconditions;
*   postconditions; and
*   changes to domain objects and relationships.

### 6. Object Design
Transform your analysis models into an object-oriented software design. Your team should determine:
*   what software objects/classes are needed;
*   what responsibilities each object should have;
*   how responsibilities should be distributed; and
*   how objects collaborate to accomplish the selected use cases.

Your design decisions should reflect the object-oriented design principles discussed in class.

### 7. Interaction Diagrams
Create UML interaction/sequence diagrams showing how software objects collaborate to realize selected use cases. The diagrams should clearly show responsibility assignments and interactions among objects.

### 8. Design Class Diagram
Develop a UML Design Class Diagram representing the final object-oriented design. It should include, as appropriate:
*   classes;
*   attributes;
*   operations/methods;
*   associations;
*   multiplicities;
*   inheritance/generalization; and
*   other relevant relationships.

## GRASP and Design Principles
Your team should explain important design decisions using principles discussed in class. For selected design decisions, explain how your design reflects relevant GRASP principles, such as:
*   Information Expert;
*   Creator;
*   Controller;
*   Low Coupling;
*   High Cohesion; and
*   Polymorphism.

You do not need to artificially use every GRASP principle. Apply them where appropriate and explain the reasoning behind important responsibility assignments.

## Mapping Design to Code and Partial Implementation
Your team should demonstrate how your object-oriented design maps to code by implementing selected parts of the Library Management System.

You are not required to implement the complete system. Each team must implement at least three selected core use cases from its design. Examples include:
*   borrowing a library item;
*   returning a library item;
*   reserving an unavailable item; or
*   another core use case approved by the instructor.

The implementation should be consistent with your object-oriented design. In particular, the implemented classes, methods, responsibilities, and object collaborations should correspond to the design presented in your UML diagrams.

A graphical user interface, database, networking functionality, or other production-level infrastructure is not required. The implementation should focus on demonstrating how the designed objects, responsibilities, and collaborations map to code.

The purpose of this partial implementation is to demonstrate the transition from design to code rather than to build a complete production-ready application.

## Progress Checks and Peer Review
There will be project progress checks during the semester. Each team should be prepared to present its current analysis and design artifacts and explain its progress.

*   **Progress Check 1:** Requirements, Use Cases, and Domain Model
*   **Progress Check 2:** SSDs, Operation Contracts, and Initial Object Design
*   **Final Stage:** Complete Design, Partial Implementation, and Project Presentation

Before the final submission, each team will review another team's draft project report anonymously. The review should identify strengths, issues, and constructive suggestions. Teams will have an opportunity to revise their designs based on the feedback. Peer feedback is intended to improve the project; the instructor determines the final project grade.

## Final Deliverables
Each team should submit the following:
*   requirements and documented assumptions;
*   use-case descriptions;
*   domain model;
*   required System Sequence Diagrams;
*   operation contracts;
*   interaction/sequence diagrams;
*   Design Class Diagram;
*   explanation of selected GRASP/design decisions;
*   partial implementation of at least three core use cases;
*   source code for the partial implementation; and
*   final project report.

## Project Presentation
Each team will give a short presentation explaining and demonstrating its project. The presentation should address:
*   the problem and major requirements;
*   the team's analysis and important domain concepts;
*   important object-oriented design decisions;
*   object responsibilities and collaborations;
*   key UML models;
*   how selected parts of the design map to code;
*   the partial implementation; and
*   major challenges, assumptions, or design changes.

All team members should participate in the presentation and should understand the team's overall design.
